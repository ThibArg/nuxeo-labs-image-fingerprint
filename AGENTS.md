# AGENTS.md

Instructions for AI coding agents working on this repository. `README.md` is the user documentation;
keep both consistent.

## What this is

A small HTTP service that embeds an invisible [TrustMark](https://github.com/adobe/trustmark)
watermark into an image, and reads it back. It runs as its own container next to Nuxeo, which calls
it with `curl --data-binary @photo.jpg`. This repository is **source only**: each user builds their
own image. No image is published.

| File | Role |
|---|---|
| `image-fingerprint/Dockerfile` | `python:3.12-slim` (Debian 13) + CPU-only PyTorch + TrustMark; downloads the model weights at build time |
| `image-fingerprint/app.py` | FastAPI service: reads the body into memory, runs TrustMark in a thread, returns the image or a JSON result |
| `image-fingerprint/THIRD-PARTY-NOTICES.md` | Apache-2.0 for this code; licenses of everything the build downloads |
| `samples/make-sample.py` | Generates `samples/photo.jpg` (synthetic, no third-party content) |
| `README-Running-at-scale.md` | Tuning: sizing, memory, CPU, replicas, and asynchronous invocation |

The image sources live in `image-fingerprint/`, which is also the Docker build context: the user
copies that folder next to their `docker-compose.yml`. **Everything the build needs must be inside
that folder** - there was once a `requirements.txt` at the repository root and the build simply could
not work. `samples/` and `README.md` stay at the root and are not part of the image.

## Repo facts

- No CI, no test suite, no build step for the repository itself. The only verification is the
  "Build, run, verify" procedure below; don't look for a Makefile, a workflow or a package manifest.
- `AGENTS.md` is committed on purpose here and must **not** be added to `.gitignore`.
- Work happens directly on `master`, and `README.md` still carries a work-in-progress banner. Don't
  remove that banner on your own initiative.
- Runtime knobs, read once at import (`app.py` top), so changing one needs a container restart:
  `MAX_UPLOAD_MB=100`, `MAX_PIXELS=30000000`, `CONVERT_TIMEOUT_S=60`, `MAX_CONCURRENT=1`,
  `TORCH_THREADS=2`, `MIN_SIDE=150`, `TM_MODEL=Q`, `TM_STRENGTH=1.0`.
- **No `LICENSE` file, on purpose**: the Apache-2.0 licensing is stated in the "Licenses" section of
  `README.md` and at the top of `THIRD-PARTY-NOTICES.md`. Don't add one. Don't turn those pointers
  into relative links either: `THIRD-PARTY-NOTICES.md` is copied into the image (`Dockerfile`) and
  ships alone with the `image-fingerprint/` folder, where `README.md` and `samples/` do not exist.

## Hard rules

- **Docker**: ask the user before building, rebuilding or pulling an image (a build downloads about
  800 MB and takes minutes), and before deleting any Docker object. If no image is available to test
  with, stop and ask. Never use `docker image prune` / `docker system prune`: they also delete other
  projects' images.
- **Nothing third-party in the repo**: no binaries, wheels, model weights, built images or vendored
  code. The build downloads them.
- **No customer or prospect data**: never commit images received from users. `samples/photo.jpg` is
  generated by `samples/make-sample.py`; if a sample is needed, generate it, don't download one.
- **No sensitive information** in any file: no secrets, tokens, internal URLs or hostnames, personal
  paths, user names, customer or prospect names.
- **Licenses**: no AGPL dependency, and keep the whole Python layer permissive (MIT / BSD /
  Apache-2.0 / PSF). This is a selling point of this image and it is stated in `README.md`: a new
  GPL/LGPL dependency would invalidate that claim. Update `THIRD-PARTY-NOTICES.md` whenever what the
  image contains changes.
- **Stable API**: Nuxeo integrations depend on
  `POST /embed?payload=<1-8 A-Z0-9>[&format=jpeg|png|webp][&strength=0.5-2.0]`, `POST /decode`,
  the raw request body, the content types, the status codes (400, 413, 500, 504) and plain-text
  error bodies (so `curl --fail-with-body` fails). `/decode` returns **200** with
  `{"present":false,"payload":null}` when there is no watermark - that is not an error and callers
  rely on it. Only add optional parameters; don't change existing behavior.
- **Never log the payload.** The token-to-recipient mapping lives in Nuxeo. The one-line request log
  carries format, size, status and duration only.
- **Security model**: no authentication, so the service must never publish a port in production.
  Keep it non-root, on a read-only filesystem with a `/tmp` volume, with the upload size limit, the
  pixel limit and the concurrency limit.
- **New source files** start with:
  `# SPDX-License-Identifier: Apache-2.0` and `# Copyright 2026 Hyland Software, Inc.`

## Why things are the way they are

- **8 characters, `A-Z0-9`**: TrustMark carries 100 bits. The default `BCH_5` schema spends 35 bits
  on ECC and 4 on the schema version, leaving 61. Text mode packs 7 bits per character
  (`DataLayer.encode_text_ascii`), so 8 chars = 56 bits fit and 9 = 63 bits do not. The charset is
  restricted so the value is safe in a URL and on a command line with no escaping.
- **`loadRemover=False`** in both `app.py` and the `Dockerfile`: the default `True` downloads
  `trustmark_rm_Q.ckpt` (77 MB, larger than the encoder and decoder combined) for
  `remove_watermark()`, which this service does not expose. **Keep the two flags identical**: if
  `app.py` asked for the remover and the `Dockerfile` had not pre-downloaded it, startup would try to
  fetch it and fail on the read-only filesystem.
- **Weights at build time**: `TrustMark.check_and_download` writes into its own `site-packages`
  directory. Pre-downloading as root during the build means the runtime user only ever reads them,
  which is what allows `read_only: true`. The checksum is re-verified at every startup; that costs
  under a second.
- **`MAX_PIXELS` and memory**: TrustMark's `encode` upsamples the residual to full resolution as
  `float32`, then mixes it with the cover as `float64` (`np.array(cover)/127.5` promotes). Measured
  cost is ~450 MB idle plus **~90 bytes per pixel**. 30 MP peaks at ~2.7 GB; at `mem_limit: 2g` the
  container is OOM-killed. `MAX_PIXELS` and `mem_limit` must be raised or lowered together.
- **The explicit pixel check in `open_image`**: Pillow's own `MAX_IMAGE_PIXELS` guard only raises
  above **2x** the value, so relying on it would silently allow double the advertised limit. The
  explicit `width * height > MAX_PIXELS` test runs after `Image.open()` (header only) and before
  `load()`, so an oversized image is rejected before any pixel is decoded.
- **`MAX_CONCURRENT=1`**: all requests share one model instance. Scale with replicas, not workers or
  threads. Two reasons, both measured and written up in the README's "Running in production":
  - **Never suggest `uvicorn --workers N`.** uvicorn spawns workers with the `spawn` multiprocessing
    context (`uvicorn/_subprocess.py`), so each worker re-imports `app.py` and builds its **own** copy
    of the model - no copy-on-write sharing. Worse, `MAX_CONCURRENT` is a *per-process* semaphore, so
    N workers allow N simultaneous conversions inside a single `mem_limit`, silently defeating the
    memory guard. The OOM killer then acts on the whole cgroup, taking the healthy requests with it.
  - **More CPU barely helps.** The model always runs on a fixed 256x256 tensor, so it is the
    full-resolution NumPy mixing that dominates large images, and that is largely single-threaded.
    Measured: 8 cores give only 1.9x on a 24 MP image (but 3.6x on a 1 MP one, where the model
    dominates), and a 24 MP embed only manages to use ~1.6 cores. `cpus: 2` with `TORCH_THREADS=2` is
    the sweet spot; setting `TORCH_THREADS` above the CPU quota is slightly counter-productive.
- **Memory budget**: `450 MB + MAX_CONCURRENT x 90 bytes x MAX_PIXELS`. `MAX_CONCURRENT` and
  `MAX_PIXELS` multiply, so they can only be raised against each other within one `mem_limit`.
- **Timeout accounting**: `CONVERT_TIMEOUT_S` is armed *after* the request acquires the semaphore
  (`run()` in `app.py`), not when it arrives. A request queued behind others can therefore take
  longer than `CONVERT_TIMEOUT_S` wall-clock, which is why the client timeout has to be the larger
  one. A thread cannot be killed, so on timeout the caller gets a 504 while the encode finishes in
  the background.
- **Aspect ratio > 2:1**: TrustMark crops the centre square, watermarks it and pastes it back
  (`get_the_image_for_processing` / `put_the_image_after_processing`). Decoding crops the same way,
  so the round-trip works, but the edges of a panorama carry no mark. This is upstream behaviour,
  not something to "fix" here.
- **Alpha**: the alpha channel is detached before encoding and put back afterwards, so transparency
  survives but is not itself watermarked. TrustMark returns an image of the same size as the input,
  which is what makes `putalpha` valid.
- **`torch.load` and `weights_only`**: torch >= 2.6 defaults to `weights_only=True`. The three
  TrustMark `.ckpt` files only contain `collections.OrderedDict`, `torch._utils._rebuild_tensor_v2`
  and storage types, so they load fine. If a future TrustMark release ships checkpoints with richer
  pickled objects, this is where it would break.
- **`kornia` is not needed** even though `trustmark/KBNet/kbnet.py` imports it and it is not a
  TrustMark dependency: only `kbnet_s_arch` is reached, and only when the remover is loaded, which
  it is not. Don't "fix" this by adding kornia.
- **Pinned torch/torchvision versions** must exist for cp312 on **both** `linux_x86_64` and
  `linux_aarch64` on the CPU index, otherwise the image builds on an EC2 box and not on a Mac (or the
  reverse). Check both before bumping. `==2.14.1` also matches `2.14.1+cpu` per PEP 440.

## Build, run, verify

There is no automated test suite: this procedure is the test. Build only after the user agreed, and
use the image tag the user gives you (`image-fingerprint` below is an example).

Run `docker ps` first: another project's compose stack may already be running an
`image-fingerprint` container. Never stop or reuse a container you did not start, and pick a port
nothing else uses.

**A change limited to `app.py` needs no rebuild**: mount the file over `/app/app.py` in an existing
image and restart the container. Use this for every Python iteration and only rebuild when the
`Dockerfile` changes.

```bash
docker run --rm -d --name if-check -p 127.0.0.1:18090:8080 \
  -v "$PWD/image-fingerprint/app.py:/app/app.py:ro" image-fingerprint:latest
```

Build, from the repository root - the build context is `image-fingerprint/`, not the root:

```bash
docker build -t <image> ./image-fingerprint
docker build --platform linux/amd64 -t <image-for-amd64> ./image-fingerprint
```

Run and check `/health` reports `"status":"ok"`:

```bash
IMAGE=image-fingerprint
docker run --rm -d --name if-check -p 127.0.0.1:18090:8080 "$IMAGE"
curl -s http://127.0.0.1:18090/health
```

Round-trip on all three output formats (each must decode back to the payload sent):

```bash
U=http://127.0.0.1:18090
for f in jpeg png webp; do
  curl -s -o /tmp/wm.$f --data-binary @samples/photo.jpg "$U/embed?payload=K7Q2M9XA&format=$f"
  echo "$f -> $(curl -s --data-binary @/tmp/wm.$f $U/decode)"
done
# and the un-watermarked original must report present:false
curl -s --data-binary @samples/photo.jpg "$U/decode"
```

Errors (each must print the code in brackets):

```bash
t(){ printf "%-30s %s\n" "$1" "$(curl -s -o /dev/null -w '%{http_code}' "${@:2}")"; }
t "[400] empty"        -X POST --data-binary @/dev/null "$U/embed?payload=ABC"
t "[400] no payload"   --data-binary @samples/photo.jpg "$U/embed"
t "[400] 9 chars"      --data-binary @samples/photo.jpg "$U/embed?payload=TOOLONG12"
t "[400] lowercase"    --data-binary @samples/photo.jpg "$U/embed?payload=abc"
t "[400] bad format"   --data-binary @samples/photo.jpg "$U/embed?payload=ABC&format=gif"
t "[400] bad strength" --data-binary @samples/photo.jpg "$U/embed?payload=ABC&strength=9"
t "[400] not an image" --data-binary @image-fingerprint/Dockerfile "$U/embed?payload=ABC"
```

`MIN_SIDE` and `MAX_PIXELS` need generated images. Use a **compressible** one for the pixel limit: a
random-noise PNG that big hits `MAX_UPLOAD_MB` first and tests the wrong thing.

```bash
docker run --rm -v "$PWD/samples:/s" --entrypoint python "$IMAGE" /s/make-sample.py /s/big.jpg 7000 5000
curl -s --data-binary @samples/big.jpg "$U/embed?payload=ABC"   # [413] over the pixel limit
```

Memory, when `MAX_PIXELS` or `mem_limit` changes. `memory.peak` is cumulative and not resettable, so
use a **fresh container per measurement**:

```bash
docker run --rm -d --name if-mem --memory=4g --memory-swap=4g -p 127.0.0.1:18091:8080 "$IMAGE"
# wait for /health, then:
docker exec if-mem cat /sys/fs/cgroup/memory.current    # idle baseline
curl -s -o /dev/null --data-binary @samples/big.jpg "http://127.0.0.1:18091/embed?payload=MEMTEST1"
docker exec if-mem cat /sys/fs/cgroup/memory.peak
docker inspect -f '{{.State.OOMKilled}}' if-mem         # must be false
```

Production shape: in `docker-compose.yml` the service runs `read_only: true` with a `/tmp` volume and
all capabilities dropped, which a plain `docker run` does not exercise. Any code writing outside
`/tmp` passes the tests above and fails in production, so re-run at least one embed per format this
way:

```bash
docker run --rm -d --name if-ro --read-only --tmpfs /tmp --cap-drop ALL \
  --security-opt no-new-privileges:true -p 127.0.0.1:18092:8080 "$IMAGE"
curl -s http://127.0.0.1:18092/health
docker logs if-ro 2>&1 | grep -iE "read-only|permission|denied|traceback"   # must be empty
```

Confirm the remover was **not** downloaded (only 3 files, no `trustmark_rm_*`):

```bash
docker run --rm --entrypoint sh "$IMAGE" -c 'ls /usr/local/lib/python3.12/site-packages/trustmark/models/'
```

Python packages and licenses, to compare with `THIRD-PARTY-NOTICES.md`:

```bash
docker run --rm --entrypoint python "$IMAGE" -c "import importlib.metadata as m; [print(d.metadata['Name'], d.version, d.metadata.get('License-Expression') or '; '.join(c.split('::')[-1].strip() for c in (d.metadata.get_all('Classifier') or []) if c.startswith('License'))) for d in sorted(m.distributions(), key=lambda d: d.metadata['Name'].lower())]"
```

Stop the containers (they are removed automatically):

```bash
docker stop if-check if-mem if-ro
```

## Upgrading

Upgrades need a rebuild: ask the user first. After any upgrade, run the whole "Build, run, verify"
procedure, then update `THIRD-PARTY-NOTICES.md` and, if they changed, the image size and the
TrustMark version shown in `README.md`.

- **Debian / Python (security fixes)**: rebuild with a fresh base image, `docker build --pull ...`.
- **TrustMark**: change the pin in the `Dockerfile`. Releases:
  https://pypi.org/project/trustmark/. Then check that:
  - the `encode`/`decode` signatures and the `(secret, present, schema)` return tuple are unchanged;
  - the default encoding schema is still `BCH_5`, otherwise the 8-character limit moves **and every
    image already fingerprinted becomes undecodable**;
  - the checkpoints still load under `weights_only=True`;
  - `loadRemover=False` still skips the remover download.
- **torch / torchvision**: check the version exists for cp312 on both `linux_x86_64` and
  `linux_aarch64` at https://download.pytorch.org/whl/cpu, and that `lightning` still allows it
  (it currently requires `torch<4.0,>=2.1.0`).
- **Everything else**: `docker run --rm --entrypoint pip "$IMAGE" list --outdated`.

## Asynchronous invocation - tested, don't re-litigate from the sources

`README-Running-at-scale.md` documents this. The findings below were **run against a real Nuxeo
LTS 2025 instance**, and several contradict what the sources suggest, so don't "correct" them by
reading `AbstractWork` again:

- **A plain Work does not retry.** `AbstractWork.getRetryCount()` returns 0. Only `ListenerWork`
  (async post-commit listeners, default 2) and BAF stream processors retry.
- **`ListenerWork` retries have no backoff.** Measured: 3 attempts (1 + 2 retries) spread over
  **48 ms**. They cannot ride out a restart of the fingerprint service. Raising `retryCount` adds
  attempts, not delay, so it does not help.
- **`Bulk.RunAction` with the stock `automation` action does not retry either**: `failOnError`
  defaults to `false`, so the error is recorded and swallowed and the `maxRetries` policy never
  fires. Measured: `COMPLETED processed=1 errorCount=1`, service never contacted.
- **BAF with `<option name="failOnError">true</option>` does work.** Measured: submitted with the
  service down, service started 2 s later, command recovered and completed with `errorCount=0` after
  ~7 s of backoff. This is the only configuration that survived an outage.
- **Nothing survives a Nuxeo restart without Kafka**, and it fails *silently*: measured, an in-flight
  bulk command was still reporting `state=RUNNING processed=0` sixty seconds after the restart, with
  the service healthy and never contacted. `nuxeo.stream.work.enabled` defaults to
  `${kafka.enabled}` = false.
- **`ConversionService.scheduleConversion` is a trap**: `ConversionWork` has 0 retries and
  `ConversionStatus` has no FAILED state, so a failure is indistinguishable from "still running".
- **Contributions in `nxserver/config/` must be named `*-config.xml` or `*-bundle.xml`**
  (`OSGiRuntimeService`). Any other name is silently ignored - no error, no warning.
- The conversion cache is **not** an idempotency guarantee: node-local, 10 MiB by default, cleared on
  restart. It did mask a stopped service during testing, which is exactly why it should not be relied
  on.
- Not tested, and labelled as such in the doc: the dead letter queue and its replay via
  `WorkManager.RunWorkInFailure`, and saving the fingerprinted blob back on the document (the test
  chain only logged, which sidesteps re-entrancy).

## Out of scope

- The Nuxeo side (mime types, command lines, converters, automation, UI) is configured in Nuxeo, not
  in this repository. `README.md` documents it as a ready-to-copy example; no Nuxeo code or bundle is
  built here. Keep that example in sync with the service API, and don't simplify away the parts that
  look redundant. The semantics below are verified against the LTS 2025 sources:
  - `enabled="true"`: the default is `false` and the command is silently ignored.
  - `-o #{outDirPath}/nxblob-fingerprinted.<ext>`: without `-o`, `CommandLineConverter` lists
    `#{outDirPath}` and turns **every** file it finds there into a result blob. The `nxblob-` prefix
    marks the name as a throwaway temp name, so `ConversionServiceImpl.updateResultBlobFileName`
    renames the rendition to the source base name plus *either* the first extension registered for
    the `<destinationMimeType>`, *or* - when that mime type declares none - the extension of the
    `-o` file name. The `<ext>` in `-o` is therefore load-bearing for unregistered mime types.
  - `application/json` and `image/webp` are **not** in Nuxeo's default mime type registry. That is
    harmless and needs **no** contribution: the registry lookup falls back to the
    `application/octet-stream` entry, which declares no extension (`nxmimetype-service.xml`), so the
    name falls back to the `-o` extension and still comes out `photo.json` / `photo.webp`. Note it
    is the *lookup* that falls back, not the blob: `updateResultBlobMimeType` sets the blob's own
    mime type from `<destinationMimeType>` regardless of registration. `README.md` used to carry a
    mime type contribution justified by the opposite claim; it was wrong and has been removed.
  - `Blob.RunConverter` `parameters` must be a `key=value` **string**. A JavaScript object is
    silently dropped: `DocumentScriptingWrapper.computeProperties` fills
    `DataModelProperties.properties` while `RunConverter.propertiesToMap` iterates the `HashMap`
    superclass, so the map arrives empty.
  - `--fail-with-body` keeps the service's plain-text error (`-f` discards it); `-H "Expect:"` avoids
    curl's 100-continue handshake on large bodies.
  - Timeout chain, each step longer than the previous one: `CONVERT_TIMEOUT_S` (60) <
    `curl --max-time` (80) < the command `<timeout>` (90s) < the transaction timeout
    (`nuxeo.db.transactiontimeout`, 300s by default). `<timeout>` is parsed as a `Duration`, so its
    unit is mandatory (`90s`, not `90`), and Nuxeo enforces
    `min(<timeout>, remaining transaction TTL)` by prefixing the command with `timeout -s 9`.
- Publishing images to a registry. This repository ships source; the licensing allows redistribution
  but nothing here is set up to publish.
